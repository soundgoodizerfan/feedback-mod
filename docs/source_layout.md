## Source layout

Root package `io.github.soundgoodizerfan.feedback`. The package tree follows the mod's **separation of systems**, not Minecraft's registry categories — measurement, control and actuation are separate systems the player wires together, and the code says so:

| Package | Holds |
| --- | --- |
| `registry/` | every `DeferredRegister` — one place to look |
| `item/` | hand-carried items — instruments (`ThermometerItem`, `CalipersItem`, `TemperatureSensorItem`), `WrenchItem` (turns a placed block a quarter turn about the face clicked, by its facing or axis property), `HandHammerItem` and its `HandToolItem`/`HandToolCrafting` base (`HandSwing`: tap/blow/heavy/mighty, sneak-scroll, hunger per St), `MoldItem`, `DataConnectorItem`, `DebugHelmetItem`, and the generated `FormItem`/`FormBlock` (one per material form, see `feedback_mechanics.md` §5.4) and `MaterialProbeItem` (debug: prints an item's material file), `MassProbeItem`/`MassProbeRecipe` (crystal plate on metal backing, cut carried as the `cut` component from `process/Cut`, an `Instrument` for `Quantity.DEPOSIT`; hangs in the electrolytic cell, mechanics 6.17), `BoardItem`/`BoardRecipe` (trace board: etched, printed or pasted, the `board` component from `process/Board`), `CircuitItem` (the Basic Electronic Circuit: carries the `circuit` component from `process/Circuit`, scorches when hot; mechanics 6.21), `SolderingIronItem` (hand route to a joint: opens `client/SolderScreen`, replays the drag server-side through `Soldering.Pass`; mechanics 6.22), `ComponentTesterItem` (an `Instrument` reading `instrument/Testable` parts; mechanics 6.20), `GloveItem` (a curio, material-rated) and `TongsItem`/`TongsRecipe` (two rods and a grip, the component carries both materials) |
| `core/unit/` | **the units of §17 as types, and the machinery for the next one.** Eighteen live: `Tu`, `TuRate`, `ThermalMass`, `Conductance`, `Su`, `Rpm`, `Fu` (an int), `XPu` (experience points, an int; the Enchanting Table's session cost), `St`, `Drag` (`Su/RPM`), `Inertia` (`Su·t/RPM`), `Vdrag` (aerodynamic drag area, block² — *not* `Drag`; V for vehicle), `Pu` (pressure, air over volume), `Mb` (volume — air so far; fluid tanks still count bare-`int` mB), `Mu` (mass, kg), `Density` (`Mu/mB`), `Qu` (amount of substance; an ingot of any metal is `FTuning.QU_PER_INGOT`) and `Eu` (electricity: a `VoltageBand` and integer amps -- the one non-scalar unit, its codecs live on the record). Any `Mu` handed to Sable goes through `Units.kpg` — 1 kpg (Sable's mass unit) = 1000 Mu. Thin records, one component *named for the dimension* — that naming is the second guard, after the parameter type. **No arithmetic on them**: they type the plumbing and the physics unwraps inline to floats, so `Heat.tick` still reads like the equation. `Unit` is the common interface, `Units` holds codec/wire/format helpers — **the checklist for adding a unit is in `Units`**. Datapack records (`Deformation`, `ThermalProcess`, `Quench`, `Material`) are typed too now, via `Units.codec`/`Units.streamCodec` so the on-disk JSON stays a bare number; `Work`, condition and ticks have no type, for stated reasons |
| `core/hazard/` | **what careless contact costs.** `HotContact` (three named bands -- scald, burn, sear -- anchored on figures the mod already has), `Shock` (by `VoltageBand`; LV keeps the bare wire's old figure), `PressureBurst` (the danger-to-critical ladder shared by the Pressure Vessel and the Boiler, plus scald and burst), `Hazards` (the three fire/armour-tagged damage types), `Protection`/`Insulator`/`Grip` (what a player has between hand and hazard: gloves in the Curios `hands` slot and tongs in a hand, each rated by its *material's* file through an exposure fraction -- no per-item rating), `HazardEvents` (the held piece and the touched block; a consequence, never a lock -- the use goes through and the hand pays). A block is hot if it is a `ThermalBody`, live if it is an `ElectricNode` with `touchVolts() > 0`; nothing asks what it is |
| `core/rotation/` | the mechanical network — `RotationNode`, `RotationNetwork`, `RotationPropagator` |
| `core/electric/` | the electrical network (`Sparks` emits the arc game event the detectors hear), `core/rotation/`'s pattern. `ElectricNode` (a block entity with a role: wire, source or sink, and a `DataNode`), `ElectricPropagator` (flood-fills a run when topology changes), `ElectricRun` (the cached routing tree and the per-tick arithmetic: pool of highest-voltage sources, proportional shares, sag, per-block drop), `ElectricRuns` (per-level registry and tick hooks). `ElectricMember` is the world-blind interface the resolver sees, which is why it is tested without blocks. `ElectricRules` holds the rulings still `[OPEN]` -- sag curve, slow-down shape, over-voltage scale -- one method each so changing one is a one-line edit |
| `core/thermal/` | the thermal model — `ThermalBody` (has a temperature and a mass), `HeatSource` (has a flame temperature and no mass; `catchUp` says what it did across a gap), `Heat` (the maths; `relax` is `tick` solved for n ticks), `Catchup`/`FireSpan` (a block back from an unloaded chunk is advanced across the gap in closed form, fuel burned for what it had; process progress is *not* advanced), `ItemHeat` (a workpiece's own heat), `AmbientTable` (the room, by dimension — datapack `ambient_temperature/`, synced to the client; `FTuning.AMBIENT_TU` is only its default) |
| `machine/` | physical operations. A machine class never names a recipe. One subpackage per machine family (`cable`, `cell`, `capacitor`, `dynamo`, `electromagnet`, `electrolytic`, `breaker`, `detector` (coherer and cat's whisker: `SparkDetectorBlockEntity` is a wire that hears the `feedback:spark` game event, mechanics 6.18), `relay` (contacts moved by an adjacent electromagnet, `ElectricMember.joins`), `oven` (reflow oven: a `ThermalBody` batch of boards graded by `process/Soldering`, 6.20), `phosphor` (phosphor screen: hot-sealed glass envelope, a `PressureHolder`, burn-in; oscilloscope: reads an adjacent `ElectricNode`, 6.20), `grindingwheel` (stone and diamond wheel, one class: the rating is the grit material's hardness, 6.19), `coil`, `condenser`, `pump`, `clutch`, `overspeedtrip`, `creative`, ...); each class javadoc states its physics and which rulings are `[OPEN]`. Electrical machines are `ElectricNode`s (source, sink or wire), thermal ones `ThermalBody`s, shaft ones `RotationNode`s. `Valve` gates an air or fluid line with one `OPEN` state |
| `process/` | operation definitions, completion, and overrun behaviour |
| `instrument/` | carried sensors. Read-only by construction — an instrument has no way to act. Electrical: `GalvanometerItem` (`Quantity.CURRENT`) and `ElectroscopeItem` (`Quantity.VOLTAGE`, coarse, never current); every `ElectricNode` is also a `DataNode` carrying its own reading |
| `control/` | controllers, timers, data links. `control/controller/`, `control/program/` and `control/programmer/` are the Tier 1 program-graph controller from `docs/feedback_controller_spec.md`: a `ProgramGraph` of sensor/comparator/actuator nodes, authored on a Punch Card by the Programmer block. `control/bimetallic/` and `control/timer/` are simpler standalone controllers (bimetallic strip, timer); `Switchable` is the on/off interface all controllers and actuators implement. `control/data/` (`DataNode`, `DataNodeRef`, `DataLinkManager`) is the data-link system's tech-demo pass — read from MrCrayfish's Furniture Mod: Refurbished's electricity system (MIT), **its `1.21.1` branch specifically, not the repo's default `26.1.2`** — check out the branch matching the target Minecraft version before reading, always. `control/Analog` is the vehicle-only exception to philosophy 13: a part a number sets by channel (engine, frame), and `control/ChannelSource` a node with several readings (the seat). `CreativeControllerBlock` (in `control/controller/`) is the controller with no power need, debug-only, same standing as `DebugHelmetItem`. The node/link overlay (`client/DataNodeRenderer`, `DeferredDataRenderer`, `DataLinkFrame`) is also from that read: a `BlockEntityRenderer` queuing draws that get flushed once a frame into vanilla's entity-outline render target, visible only while the connector is held |

Gauges are `Gauge` suppliers drawn through `GuiSkin.gauge`. Create a package when there is something to put in it; don't scaffold empty ones.

**Datagen covers generated forms only.** `src/generated/resources` is a resource root and is committed; `runData` writes the models, block states, loot, pickaxe tag and compression recipes for generated material forms (`FormItemModels`, `FormData`) and must be re-run when a material or form type is added. Everything else -- blockstates, models, loot tables, lang, crafting recipes and recipe-unlock advancements are all hand-authored under `src/main/resources` for now. Convert when the roster is big enough that hand-editing starts going wrong — not before. The recipe pass (19 shaped recipes, 3 advancements) was the closest call so far and hand-editing still won.

**All art is placeholder.** Every item and block model points at a texture under `assets/feedback/textures/` copied from `../Texture-reference` (Malcolm Riley's `unused-textures`, CC BY 4.0) — no model references a vanilla sprite any more, apart from vanilla *parents* (`item/generated`, `block/cube_all`, `block/orientable`) **and the blocks that replace a vanilla block (furnace, blast furnace, smoker), which wear vanilla's own textures on purpose**; the Improved Furnace and Annealing Furnace keep placeholder art in models of their own. The other cloned repos (Auseawesome CC0, cleannrooster MIT, Foreck CC BY 4.0) are available but unused; **Futureazoo's is CC BY-NC-SA and must not be used.** Every copied file is listed in `THIRD-PARTY-LICENSES.md` — **add the row in the same change that copies a texture**, and don't bulk-copy a repo. No Create asset may ever be used here: Create's *code* is MIT, its *assets* are All Rights Reserved. `THIRD-PARTY-LICENSES.md` records what we owe and to whom.

### The thermal model, in one paragraph

Heat flows on a **difference**, never at a flat rate: `conductance × (fire − vessel)` in, `leak × (vessel − ambient)` out, divided by thermal mass. This matters because the flat-rate version — which is what gets written first — makes a vessel settle at `supply ÷ leak`, so insulating a crucible raises its final temperature without limit and insulation becomes a trap rather than an upgrade. Driving on the difference means a vessel approaches its fire's temperature and can never pass it, so the only way past a flame is a hotter flame, which is exactly what the bellows sells. It also pays for the slice's lava for free: lava is a fire fixed at 1200 Tu, so a crucible over lava sits just under 1200 Tu forever — the most stable heat source in the game and permanently too cool for steel. Nobody wrote that rule.

Typing the model turned up something the code had not been saying: **a vessel's leak and a fire's conductance are the same dimension** (`Work/t/Tu`), and `Heat.equilibrium` had been adding them together correctly all along. They are one type now, `Conductance`, in two roles — a leak *is* a conductance, and calling it a leak is a statement about whether you wanted it.

A **workpiece** is different again. It stores the temperature it was last stamped at plus the tick that happened on, and its current figure is computed on demand — so it cools in a chest, in a hopper, in an unloaded chunk and in a mod we have never heard of, because nothing has to remember to cool it. Item cooling is deliberately **linear** rather than exponential: an exponential never arrives, needs an arbitrary floor to stop it, and buries the whole working window in a flat tail. A constant rate makes *"you have fourteen seconds to reach the anvil"* literally true, which is what the player is actually budgeting against.

### The rotation network, in one paragraph

A `RotationNode` is a block entity that knows its own speed and which neighbour drives it. It cannot tell on its own whether it is overloaded — that is a whole-network question, answered by `RotationNetwork` (the Su ledger) and pushed down. When anything changes, `RotationPropagator` **rebuilds the entire connected run**: flood fill, find the strongest source, walk outward assigning speeds. Create propagates incrementally instead, and needs a "flicker score" to break blocks caught in propagation loops; a rebuild visits each node once and cannot loop, so we don't. Overstress reads as zero speed everywhere, but propagation deliberately uses *theoretical* speed — otherwise an overloaded network would tear itself down and rebuild the instant the load came off.
