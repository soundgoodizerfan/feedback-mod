# Combat integration map (read-only survey, 2026-10-21)

Working note for `docs/feedback_combat_spec.md` §9. Paths are under `src/main/java/io/github/soundgoodizerfan/feedback/`. Nothing here is built. Facts found while surveying that change the spec's premises are flagged **NOTE**.

## 0. Headline facts

- **There is no custom melee attack path.** Melee is vanilla's click, cooldown and point-pick, with attributes written from the bake. Everything modular hooks `LivingIncomingDamageEvent`, not the swing.
- **NOTE: a Parry already exists** as a shield trait (`modular/trait/Parry.java`, the buckler). Deflect (kite shield) already returns projectiles. Spec §9.3's "block with a held weapon" has no weapon-side hook yet; only shields reach `onShieldBlock`.
- **No Player attachments, no capabilities on entities, no mob goals, no camera/time code.** All per-player state is server-side `Map<UUID,...>` (`WielderState`), lost on restart, never synced. Skill points have no home yet.
- Curios `hands` slot only. No custom slot defs, no curio renderer.

## 1. Melee resolution today

- `modular/ModularItem.java:86` `postHurtEnemy` only costs 1 durability. Attack damage, speed and reach are vanilla attributes written by `modular/ModularStacks.java:173-182` (`ATTACK_DAMAGE`, `ATTACK_SPEED`, `ENTITY_INTERACTION_RANGE` from `Fig.DAMAGE/ATTACK_SPEED/REACH`). Vanilla's cooldown, sweep and crit run unchanged.
- `modular/ModularTraits.java:337` `onHurt(LivingIncomingDamageEvent)`: if `source.getEntity()` is a LivingEntity and `getDirectEntity()==attacker` (so melee only, not projectile), reads the **main hand** stack's trait and calls `onAttack(event, attacker, weapon, params)`. Off-hand is never consulted, so dual wield has no melee hook. `:346` `onWornHurt` does the same for armour traits (first piece per trait id, `worn()` at `:301`). `:364` knockback, `:383` worn tick, `:392` left-click-block, death at `:~410`.
- Traits are one class each in `modular/trait/` (Backstab, Flurry, Overhead, Hack, Lunge, Fork, Pierce, ...), all `onAttack` mutating the event amount. `Flurry.java:47` keeps a per-wielder combo run in `WielderState` (`trait/WielderState.java`, UUID map cleared on death/logout), reset by `Flurry.onHurt` at `:61`.
- `modular/MaterialPerks.java:98` second melee listener (smite, impaling, fire aspect, echo) off material files. Same `getDirectEntity()==attacker` gate. Also `:121` player tick burns hand (flame in hand).
- `modular/trait/SpearCharge.java`: the only existing non-click melee. Server-side swept-ish test each `PlayerTickEvent.Post` (`:264`) over entities in a reach cone with per-tick position diff; client key via `client/SpearClient.java:95` (heartbeat `SpearChargePayload` every 10 ticks, server times out at 25). `:279` cancels crits via `CriticalHitEvent`. Cancels close-range jabs in `onAttack` (`:111`). This is the best in-repo precedent for a held, server-validated, tick-driven attack; a swept hitbox would copy it.
- `item/HandSwing.java` is hand tools only (tap/blow/heavy for forging). Selected by sneak-scroll (`client/ToolScroll.java:44`, `ToolScrollPayload`). Unrelated to weapons; no conflict.
- `core/Haste.java:33` `rate()`/`time()`: Haste/Fatigue divide mod timers. Melee cadence follows via the attack-speed attribute (vanilla). Any parry window, recovery or roll cooldown should go through `Haste.time` (open item 5 in spec §8).
- **Bulwark** `modular/trait/Bulwark.java`: `onShieldBlock:50` forces block on all angles unless `BYPASSES_SHIELD`, caps blocked damage at `capacity * 1.5`, shield wear x`wear_mult`. `onUseTick:~62` applies `Burden` slow. `use:~67` bash: only when `isSprinting()`; hurts hostiles in a cone within `range`, knockback, `player.getCooldowns().addCooldown(item, Haste.time(bash_cooldown))`, `shield.hurtAndBreak`. Cooldown is the vanilla per-item `ItemCooldowns`, so any combat state that wants "can't act" can reuse it; but it is keyed on the item, so dual shields share one.
- Shield pipeline: `modular/ModularEvents.java:109` (registered at `Feedback.java:99`, normal priority) caps blocked damage to `Fig.CAPACITY`; `modular/RangedDispatch.java:122` (`EventPriority.LOW`) then calls the shield's trait `onShieldBlock`. Both use `blocker.getUseItem()`; they only fire when vanilla decides the shield is up and facing (5-tick raise delay).
- `Parry.java:44`: window = `blocker.getTicksUsingItem() < 5 + parry_ticks` (6). In window: full block, no shield damage, `attacker.knockback(...)`, HUD toast via `HudReadouts.send`. **Conflict/hook**: a new parry key either must set the same condition (shield up and used ticks) or replace this hook; a weapon parry cannot go through `LivingShieldBlockEvent` (vanilla only fires it for shields). It must act in `LivingIncomingDamageEvent` (highest priority, before `ModularTraits.onWornHurt` and `ThrownWeapon.onIncomingDamage`) or `LivingDamageEvent.Pre`.
- Order hazards on `LivingIncomingDamageEvent`: `ModularTraits.onHurt`, `ModularTraits.onWornHurt`, `MaterialPerks.onHurt`, `RangedDispatch.onArrowHit`, `Flurry.onHurt`, `ThrownWeapon.onIncomingDamage` (x1.25 wound when HELD, `ThrownWeapon.java:286`, registered `Feedback.java:98`). A parry that cancels must run first (EventPriority.HIGHEST) or other listeners still stack effects on a cancelled hit; `isCanceled` is honoured by default subscribers only if they use `receiveCanceled=false` (default), so cancel is clean.
- Knockback/stagger: only `LivingEntity.knockback` direct calls (Parry, Bulwark, Hook) and `hurtMarked=true` for velocity sync. No hurt-stun, no `LivingKnockBackEvent` source other than armour traits (`Braced`). No "stagger" state exists.
- `GunShots.java:647/656` set `target.invulnerableTime = 0` for pellets; any melee i-frames/parry-invulnerability should keep that in mind (i-frames on a rolling player vs gunfire).

## 2. ThrownWeapon / harpoon HELD

File `modular/ThrownWeapon.java` (519 lines), an `AbstractArrow` subclass. Mechanism:

| Piece | Where | Harpoon-specific? | Generic? |
| --- | --- | --- | --- |
| `HELD` static `IntOpenHashSet` of entity ids | `:283` | name | **generic**: "target has a barb in it", server only |
| `onIncomingDamage` x`HELD_WOUND_MULT` (1.25) | `:286`, tuning `ModularTuning.java:250` | wound multiplier is a harpoon rule | the hook point (damage taken by a held target) is generic |
| Set on hit: `DATA_HOST` id + `HELD.add` | `:430-436` in `onHitEntity`, gated `flight.rope()>0 && flight.pull()>0 && target instanceof LivingEntity && alive` | yes (rope+pull) | trigger is harpoon |
| `DATA_HOST` synced entity-data int | `:102` | no | sync of "who am I attached to" to client |
| `rideHost` (weapon follows target at 60% height) | `:~245` | yes (weapon rendering) | no |
| `reel(owner, host)` pulls host toward owner at `pull` x water mult x (1-knockback resistance), lift, `fallDistance=0`, `hurtMarked`; ends on `REEL_MAX_TICKS` (100), distance <= `REEL_STOP_DISTANCE` (2.5), owner/host dead | `:264-281` | **yes**: this is the rope. The *only* effect on the target is a velocity override | the knockback-resistance scaling and the end conditions are generic |
| `detach()` clears `HELD` and `DATA_HOST`; `remove()` also clears `HELD` | `:292-302` | no | **generic** release |
| host gone while attached: detach and return | `:~220` | no | generic |
| Rope render (sagging line weapon-to-hand) | `client/ThrownWeaponRenderer.java:77-115` | yes | no |

Verdict: HELD is an id set with no owner, no duration, no strength, no source. To share it (grapple hook, net, bear trap) the clean extraction is a small `Held` registry: `Map<entityId, Hold{sourceId/owner, kind, expiresTick, damageMult, moveBlock?}>` on the server plus a synced flag for the client, with `detach` becoming `Held.release(id, hold)`. Pieces that must stay harpoon-side: rope length, reel velocity (that is one *kind* of hold effect), renderer, `rideHost`. Generic effects a hold could declare: wound multiplier (now hard-coded to 1.25 for all HELD), "cannot sprint/jump/roll" (needs a hook that does not yet exist), "cannot be staggered out of". Gaps to flag: HELD is static and non-persistent (lost on restart, an entity unloaded mid-hold leaves a stale id until `remove`); it holds only one source per entity (set semantic, so two harpoons release the first when either detaches: `detach` removes the id even if another harpoon is still in). Needs a count or per-source map before sharing. No mob AI reads HELD; a held mob keeps trying to path (velocity override each tick fights navigation).

## 3. Curios

- Dependency: required, `neoforge.mods.toml` (`curios` `[9.5.1,10)`); compile `build.gradle:127`.
- Only code: `core/hazard/Protection.java:28/67` (`CuriosApi.getCuriosInventory(player).findCurios(s -> s.getItem() instanceof Insulator)`), summed with both hands (`:60-72`; max not sum). That is read every use by `HazardEvents` (player tick, right click). `GloveItem` (`item/GloveItem.java`) holds a `ResourceLocation material` and implements `Insulator` (`handlesUpToTu`, `shockProofVolts`) via `Grip.safeUpTo(level, material, FTuning.GLOVE_EXPOSURE)` / `Grip.insulates`. Material-rated: the item has no figure, `Grip.material(level, id)` reads the material file. Same recipe for a combat figure: a gear curio asks the material for hardness/density/etc.
- Slots: data only. `data/curios/tags/item/hands.json` lists `feedback:leather_gloves`; `data/feedback/curios/entities/player_hands.json` assigns the slot `hands` to `minecraft:player`. `hands` is a **Curios built-in** slot name, so no slot definition file (`data/<ns>/curios/slots/*.json`) exists in this repo. No lang for slot, no renderer registration (no `CuriosRendererRegistry` call anywhere), so gloves are invisible on the body.
- To add a slot: a `data/feedback/curios/slots/<name>.json` (size, icon, order), a tag `data/curios/tags/item/<name>.json`, an entity assignment file, lang `curios.identifier.<name>`, and slot icon under `assets/curios/textures/slot/` (or mod namespace). To render: `CuriosRendererRegistry.register(item, Renderer::new)` on the client mod bus (`FClientSetup` is the place). No Curios events used; curio equip/unequip callbacks (`ICurioItem`) not used either, which means the glove is purely queried.
- Conflict: Curios gear for combat (rings, charms, "perks") is a natural fit but must follow the hard rule that figures come from a material file, not per-item rows. Also `Protection.carried` collects hands + curios per call, an easy scaling cost if combat asks every hit.

## 4. Keys and client input to server

- Keys: `GunClient.java:~95` defines `KeyMapping` statics (`RELOAD` R, `FIRE_MODE` V, `UNLOAD` U, category `key.categories.feedback`, lang `en_us.json:159`); registered at `client/FClientSetup.java:122-126` (`RegisterKeyMappingsEvent`). Other input handlers: `DriverSeatKeys.java:47` (`InputEvent.Key`), `ToolScroll.java:44` (`MouseScrollingEvent`), `FrameGizmo.java:152` (`InteractionKeyMappingTriggered`), `SpearClient.java:95` (`ClientTickEvent.Post` on `options.keyUse`).
- Gun owns attack/use while held: `GunClient.java:125` `InteractionKeyMappingTriggered` cancels attack (and use) and `setSwingHand(false)`. A parry key bound to use or attack must cooperate with this (gun-fu), and a roll key should avoid R/V/U.
- Pattern: client acts first (flash, sound, kick), then `PacketDistributor.sendToServer(record)`. Payloads are records with `TYPE` + `STREAM_CODEC` + a static `handle(payload, IPayloadContext)` calling `context.enqueueWork`, registered in `Feedback.java:137-` (`event.registrar("3").playToServer/Client...`, protocol string `"3"`; a new payload needs no version bump unless wire-incompatible). Examples: `net/GunFirePayload.java` (yaw, pitch, aimed, offHand; handler validates item in hand, finite floats, spectator), `SpearChargePayload` (bool held + heartbeat), `GunReloadPayload` (bool, held-state), `ToolScrollPayload`.
- Server-side validation precedent: `GunShots.accept` (`:155-166`) enforces cycle with `System.currentTimeMillis()` and a tolerance (quarter cycle or `GUN_FIRE_TOLERANCE_MS`), per player+hand in `NEXT_OK` (HashMap, never pruned except by key reuse). A parry/roll key needs the same: server decides success from its own tick, not the client's timestamp.
- Prediction/reconciliation: **none really.** The client simply plays effects and trusts the server for outcome (spec 7 "prediction" comment in `GunFirePayload`). The camera kick is purely local (`GunClient.java:~335` writes `player.setXRot/YRot` directly each frame, eased by wall-clock). No rollback, no ack payload. A parry (server-decided on the incoming hit) will arrive *after* the hit: client needs a server-to-client "parried" payload (like `SpearStagePayload`/`HudReadoutPayload`) to fire hit-stop/flash; the client cannot know the outcome earlier. Latency window: the press reaches the server up to ping later than the hit, so parry window should be defined in server ticks from press receipt, with a small grace.
- Roll/movement: no client movement override exists; the only movement mods are attribute modifiers (`Burden.java:~48` transient `MOVEMENT_SPEED`, cleared on player tick) and velocity writes with `hurtMarked` (server) plus `ClientboundSetEntityMotionPacket` (`Smash.java:~75`). A roll must be client-authoritative for the local player's motion (vanilla player movement is client-authoritative), so the server mostly validates cooldown/stamina and grants i-frames.

## 5. Per-player persistent data

- Searched: no `AttachmentType`, `IAttachmentHolder`, `getPersistentData`, or `registerEntity` capabilities. `registry/FCapabilities.java` registers block-entity item/fluid handlers only.
- State on items: data components (`registry/FDataComponents.java`, `FModular`, `FWeapons`): figures, design, wear (`ModularStacks.broken/figures/design`), gun `MAGAZINE`, `MAGAZINE_SIZE`, fire mode. Item state syncs with the stack.
- State on players: server `HashMap<UUID,...>`: `WielderState<T>` (trait runs, cleared on death/logout; `Flurry`, worn-last sets), `SpearCharge.CHARGES/SPENT`, `GunShots.NEXT_OK` and `RELOADS`. Not persisted, not synced. HUD feedback goes through `HudReadouts.send(player, Component, ticks[, priority])` (S2C `HudReadoutPayload`) as transient text only.
- Where skill points fit: needs a **new `AttachmentType<SkillPool>`** (NeoForge `DeferredRegister<AttachmentType<?>>` with `serialize(codec)` + `copyOnDeath()` + `sync(StreamCodec)` for the owner). Nothing in the repo is a template for this, so it adds a registry in `registry/` (the CLAUDE.md layout says one place per `DeferredRegister`). Sync on login (`PlayerLoggedInEvent`) and change. Alternatives: a component on a worn "journal" item (rules-friendly, loses points when lost) or world-saved-data per UUID. Rule check: points must change a figure or open a move; they must not gate capability or key on item ids.
- Stagger/held/roll i-frames on arbitrary entities (mobs): the same gap. `HELD` is the only per-entity combat state; it is a bare static set. A shared `CombatState` attachment on LivingEntity (stagger-until tick, held, parry-until tick) would replace several static maps.

## 6. Client render hooks

- HUD: `RegisterGuiLayersEvent` at `client/FClientSetup.java:115` calls `GunHud.register` (`registerAboveAll(gun_ammo)`, `GunHud.java:57`), `HudReadouts.register` (`hud_readouts`, `HudReadouts.java:75`, text toasts with fade), `BuildToolHud.register`. A flash/vignette layer is one more `registerAboveAll`; they draw in `GuiGraphics` with `GuiStyle.hudCard` and `SKIN.ink()` colours.
- Per-frame: `GunClient.onFrame` on `RenderFrameEvent.Pre` (`:148`) runs fire loops, aim easing and `applyKicks` (writes player rot directly by wall-clock ms, not partial tick). `ComputeFovModifierEvent` (`:139`) for aim zoom, so FOV punch is a precedent. `ClientTickEvent.Post` in `FrameGizmo`, `GunSmoke`, `SpearClient`. `RenderLevelStageEvent` in `SoundingOverlay:63` and `DataLinkFrame:42` (world-space overlays with `RenderSystem`, deferred render target).
- **Absent**: camera angle/roll event (`ViewportEvent.ComputeCameraAngles`) not used anywhere, so a roll-based shake has no home yet (the existing "shake" is a rotation mutation, which also changes where the player aims; hit-stop shake should use ComputeCameraAngles or it will move the crosshair). No `Timer`/`tickrate`/partial-tick manipulation anywhere in client code (`grep` empty). Hit-stop options: (a) freeze the *attacker's* animation by holding the swing progress/`attackAnim` and arm pose (`IClientItemExtensions` pose hook, precedent `SpearPose`), (b) pause via client `Minecraft.getTimer()`-style slow-down, which is global and invasive in multiplayer (do not touch the logical server tick), (c) freeze only affected entities by setting their `tickCount`/render partial. (a)/(c) are the safe ones. Entity hit-flash: `LivingEntityRenderer` overlay via `RenderLivingEvent` (not used yet).
- Renderers that touch items: `SpearPose`, `ThrownWeaponRenderer`, `FrameRenderer`, `ModularReadings`. Particles/sound: `GunSmoke` (client tick particles), `FSounds.UI_*` aliased to vanilla events.

## 7. Mobs

- **There is no mob AI code in the mod.** No `Goal`, no `GoalSelector`, no custom entity extending `Mob`. (Only entity types: `FEntities` thrown weapon, driver seat, frame bodies.)
- Mob gear: `modular/ModularEvents.java:71` `onEntityJoin` converts `EquipmentSlot` stacks on mobs to modular via `ModularConvert.convert(held, salt)` (seeded by mob UUID and slot, `modular/ModularConvert.java`, `convertible` at `~:56`). So a zombie with an iron sword has a modular sword with baked figures. Mob melee then runs the vanilla `MeleeAttackGoal` -> `doHurtTarget` -> `LivingIncomingDamageEvent` (attacker = mob, `getDirectEntity()==mob`) -> `ModularTraits.onHurt` reads the mob's **main hand**: so weapon traits (Flurry, Backstab, ...) already work for mobs (hence `Flurry.onHurt` keys on UUID not Player). Mobs have no player tick: `onWornTick` is player-only (`ModularTraits.java:~383`), `SpearCharge` is player-only, shield `use`/`onUseTick` bash is player-only; vanilla mobs raise shields only via vanilla goals and `LivingShieldBlockEvent` still fires, so `Parry` trait applies to a mob's raised shield (ticks-using-item is meaningful for mobs that `startUsingItem`; vanilla Piglin Brutes/Vindicators do not).
- No gun AI: `GunItem` firing is a client input and `GunShots.trigger` takes a `Player`. Mob guns would need a ranged-attack goal (vanilla `RangedAttackMob`/`RangedBowAttackGoal` is `BowItem`-specific) plus an adapter around `GunShots.shoot`. Not present, not stubbed.
- A mob-parry or telegraph needs: (1) a goal added on `EntityJoinLevelEvent` (the same place gear is converted, `ModularEvents.java:71`), (2) a wind-up state (telegraph) that is networked: `EntityDataSerializer`/`SynchedEntityData` cannot be added to vanilla mobs, so use the proposed attachment + sync payload or `broadcastEntityEvent` bytes (precedent: `SpearStagePayload`, `HudReadoutPayload`), (3) a way to read incoming mob attacks before damage (the `LivingIncomingDamageEvent` point works), (4) mob stagger via `Mob.goalSelector` flag-disable for N ticks plus `getNavigation().stop()`. Mob "mass" stand-in is open in spec §8: nothing in the repo derives `Mu` for entities (units exist, `Mu` and `Units.kpg`), so it is new.

## 8. Sable

- Sable is a hard dependency used for vehicles (`vehicle/`, `client/FrameRenderer.java:290-296` `SubLevelContainer`, `client/BlockLoops.java:172` `projectOutOfSubLevel`, mass via `Units.kpg`). No weapon code references Sable: `GunShots` clips with `level.clip(ClipContext)` and `ProjectileUtil.getEntityHitResult` (`:631-635`) in the main level coordinate space; it does not project through sub-levels. Melee uses vanilla's `pick`, which is in the world/level the player's eye is in.
- A swung weapon hitting a Sable body: vanilla `Player.attack` targets entities only; blocks of a sub-level are not entities, so a "swing at a ship" is only possible if Sable itself maps the pick into the sub-level (Sable's own mixins, not Feedback's). A custom swept hitbox that calls `level.clip` or `getEntities` in plane coords would miss sub-level blocks and *entities riding a sub-level* (their positions are in a plot/local space unless `SableCompanion.projectOutOfSubLevel` is applied). Brief conclusion: no hook today; if combat on moving ships matters, run the hitbox through `SableCompanion.INSTANCE.projectOutOfSubLevel(level, pos)` as `BlockLoops` does.

## 9. Baked figures that can drive parry, recovery, stagger

Baked by `modular/ModularBake.java:melee()` (`~:315-390`) into `ModularFigures` (`modular/ModularFigures.java`, `enum Fig`), stored on the stack; client reads `ModularStacks.figures(stack)` (`ModularStacks.java:~88`).

| Fig | Defined | Meaning | Candidate use |
| --- | --- | --- | --- |
| `MASS` (Mu) | `:384` | summed part masses | stagger inflicted/resisted; parry force |
| `SWING` / `ATTACK_SPEED` | `:386-387`; `swing = clamp(SWING_K / (inertia + BALANCE_K*moment)^SWING_EXP, 0.4, 4)` | swings per second from moment of inertia about the hand | recovery time, parry-window length (a light weapon turns faster) |
| `IMPACT` | `:~373` `0.5 (headmass + ROD_STRIKE_SHARE rodmass) * tip^2`, `tip = reach*swing*pi` | Joules a blow carries | stagger magnitude vs target `Mu`; knockback; hit-stop length |
| `BALANCE` | `:385` | moment/(mass*length), 1 = head-heavy | recovery penalty (head-heavy recovers slowly), parry quality |
| `REACH` | `:388` extra range over `REACH_REFERENCE` 0.9 m, x`REACH_PER_METRE` 2 | | hitbox length |
| `JOINT` | `:389`, `joint()` | leverage over joint strength; over 1 works loose | cost of a bad parry / blocking a heavy hit (wear by misuse), exactly spec §5 |
| `BITE` | per head | edge cutting | none for parry |
| `CAPACITY` | shields `:260` | max damage stopped outright | shield stagger absorb |
| `SLOW` | armour | movement given up | roll cost |

- Head shape: **there is no shape enum.** `Edge` (`modular/Edge.java`: KEEN/STANDARD/BLUNT bite/chip) is the grind, not the geometry. Head kind is a free string: `ModularHeads.kindOf(part, role)` (`ModularHeads.java`) -> the head part item path (`pickaxe_head`, ...), with `type.strike()` the shape-to-damage factor and `Role.strike(part)`. Variants carry `params` (`param(role, part, "joint_mult")`, `ModularBake.java:~278`). Spec §8's open question stands: add a `head`/`hitbox` field to `ModularType` forms/variants (data) rather than keying on the part-kind string; hitbox length is already derivable from `reachLength`.
- Per-weapon-type behaviours live in trait `params` (`ModularTrait.Params`, data in `modular_type/*.json`); `Parry`'s `parry_ticks`, `cone`, `knock` are the existing pattern for a weapon-class parry window.
- Material side: `MaterialPerks` (smite, impaling, fire aspect, echo) are per-material qualitative effects, a pattern for per-material combat perks. Mob mass has no source (see 7).

## 10. Five riskiest conflicts

1. Damage-event ordering: parry/roll i-frames must cancel in `LivingIncomingDamageEvent` at HIGHEST before `ModularTraits.onHurt`, `onWornHurt`, `MaterialPerks`, `Flurry.onHurt` and `ThrownWeapon.onIncomingDamage`, else a parried hit still stacks perks or resets combos; weapon parry cannot use `LivingShieldBlockEvent` (shield-only).
2. Parry on the existing buckler `Parry` trait plus vanilla shield raise: a new parry key duplicates or fights the use-key shield path (5-tick raise, `getTicksUsingItem`), and the gun cancels attack/use clicks (`GunClient.java:125`), so key choice and gun-fu interplay need one input owner.
3. No player/entity state store: skill points, parry-until, stagger, held, roll i-frames have no attachment; today everything is static server maps (`WielderState`, `HELD`, `NEXT_OK`) that are lost on restart and never synced; a single `AttachmentType` with sync is the first thing to build, and `HELD` is a single-source id set that breaks if shared.
4. Client feel is local-only and server-authoritative outcome: no prediction, no camera-angle event, no time control, existing recoil mutates player rotation (moves the crosshair); a parry result arrives after the hit by latency, so hit-stop/flash need an S2C payload and must not use rotation writes or touch the logical tick.
5. Melee has no custom path: a swept hitbox must replace or run beside vanilla's click-pick/cooldown/sweep and crit (`SpearCharge` cancels crits; `ModularTraits.onHurt` only reads main hand, so dual wield and kicks bypass trait hooks); mobs use the same event path but have no goals, so telegraph/mob-parry require new AI and a sync mechanism.
